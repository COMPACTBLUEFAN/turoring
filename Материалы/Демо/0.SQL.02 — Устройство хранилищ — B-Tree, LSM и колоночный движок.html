Страничная архитектура (PostgreSQL, SQLite, MySQL InnoDB)

В реляционных СУБД файл базы разбит на страницы фикс. размера (обычно 8 КБ). Внутри страницы используется архитектура Slotted-Page. Слот-массив растёт сверху вниз, а кортежи данных пишутся снизу вверх. Указатель на кортеж (RID) — это (page_id, slot_number).

💡 Почему это гениально: Внешний индекс (B-Tree) хранит адрес записи как Slot ID, а не смещение байта на диске. Если запись изменила размер и сдвинулась внутри страницы — индекс снаружи не меняется, меняется только смещение внутри слота!

LSM-Tree: быстрая запись и сброс на диск (RocksDB, Cassandra)

В LSM запись всегда последовательна: сначала пишется в WAL (диск) и в MemTable (в памяти, SkipList). При заполнении порога MemTable сбрасывается в неизменяемый SSTable на диске. Фоновый процесс сливает файлы через Merge-Sort.

SSTable сегментов на диске пока нет. При 4 записях MemTable сбросится сюда.
💡 Фильтр Блума (Bloom Filter): Чтобы при поиске несуществующего ключа не читать 20 файлов с диска, каждый SSTable держит компактный фильтр Блума в RAM. Он мгновенно говорит: «Ключа ТОЧНО нет в этом файле» (0 I/O на диск).

Строковое хранение vs Колоночное (OLTP vs OLAP)

Журнал на 300 000 вызовов LLM (11 колонок: id, дата, модель, токены, цена, latency, статус, prompt, response). Попробуйте выполнить два разных типа аналитических запросов.

Строковая база (SQLite / PostgreSQL)
Хранит данные целыми строками по 8 КБ страницам
184.5 мс
Прочитано с диска: ~198.4 МБ
Колоночная база (DuckDB / ClickHouse)
Хранит каждую колонку в отдельном сжатом векторе
5.2 мс
Прочитано с диска: ~3.8 МБ
💡 Что произошло: В запросе агрегации DuckDB прочитал только 2 колонки (day и cost_rub), полностью проигнорировав тяжёлые строки prompt и response. SQLite был вынужден поднять с диска все 200 МБ таблицы, чтобы достать 2 числа из каждой строки.
