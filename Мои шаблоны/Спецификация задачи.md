# 📋 Спецификация: [Фича или задача — глагол + объект]

> Шаблон SDD (Spec-Driven Development). Пишется **до кода**. Черновик может писать агент; ревью и решения — твои. После утверждения по ней пишутся тесты, затем код. Агенту-кодеру тесты менять нельзя.
> Дата: ДД.ММ.ГГГГ · Статус: черновик / на ревью / утверждена · Проект: [...] · Ветка: `spec/...` · Автор черновика: ты / агент · Ревью и решения: ты

## 🎯 Цель
Что должно работать после выполнения — одно проверяемое предложение, с числом, если оно есть.

## 📦 Контекст
- **Зачем:** какую проблему решаем, для кого; какая это задача в дереве декомпозиции.
- **Что уже есть и не трогаем:**
- **Стек и версии:**
- **Файлы, которые нужны агенту для контекста:**
- **Архитектурное решение:** где живёт логика и где — тонкая обёртка (интерфейс: CLI, API, MCP); что из этого переиспользуется дальше.

## ➡️ Вход
Формат, типы, ограничения. **Примеры вызова** — 2–3 штуки «вызов → результат», чтобы не гадать, что функция принимает и возвращает.

## ⬅️ Выход
Формат, примеры, граничные случаи (пусто, ноль, максимум).

## ⚠️ Ошибки
Каждая ошибка — по слоям: что делает ядро и что видит пользователь.

| Ситуация | Ядро (исключение) | Интерфейс (код возврата, статус) | Сообщение |
|---|---|---|---|
| | | | |

**Порядок проверок** — что проверяется первым, если вход нарушает несколько условий сразу: `[1. … → 2. … → 3. …]`. Без этой строки агент выберет порядок сам.

## 🔒 Инварианты
Что верно **всегда** или **никогда** — для любого входа, а не для одного примера. Каждый проверяется тестом-свойством.

| Инвариант («всегда / никогда») | Как проверяется (стратегия входов → свойство) |
|---|---|
| | |

## ✅ Критерии приёмки
Каждый критерий — проверяемый, с числом, если оно есть. **У каждого — способ проверки**: тест-кейс (номер), тест-свойство, замер (с условиями: что мерим, на чём, сколько прогонов), ревью или линтер. Критерий без проверки — ещё не критерий. Задача принята, когда все строки ✅; номера сквозные — на них ссылается таблица тест-кейсов.

**Функциональные** — что задача делает.

| № | Требование | Как проверить | ✅ |
|---|---|---|---|
| 1 | | Кейсы №…: что запускаем и что сверяем | ☐ |

**Нефункциональные** — насколько хорошо: скорость, память, безопасность, надёжность, сопровождаемость. Если это требование ко всей системе из design doc — ссылка на него (`design doc §N`), а здесь только число и проверка для этой задачи. Общие правила проекта (как мерить, как писать тесты) не повторяются — ссылка на них.

| № | Вид | Требование | Как проверить | ✅ |
|---|---|---|---|---|
| 2 | | | | ☐ |

**Образец строки** (другая задача): `2 · Скорость · поиск по тегу на хранилище из 1 000 заметок — ≤ 50 мс в 95 вызовах из 100 · тест-замер: синтетическое хранилище в tmp_path, 100 вызовов функции ядра, 95-й по скорости ≤ 50 мс · ☐`

## 🚫 Ограничения и не-цели
Чего не делаем и что нельзя менять (схема БД, публичный интерфейс, зависимости). Не-цели — со ссылкой, какая задача их возьмёт.

## 🛡 Безопасность
Какие данные проходят через фичу, кто к ним имеет доступ, что будет при вредном вводе (в том числе prompt injection, если есть LLM). Проверки входа — через `if …: raise`, не `assert` (его отключает `python -O`). Что нельзя показывать в сообщениях об ошибках.

## 🧪 Тест-кейсы (Red)
Классы — обычный, граничный (на границе и на шаг за ней), ошибочный, безопасность. У каждого кейса — критерий, который он проверяет.
